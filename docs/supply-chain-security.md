# Supply Chain Security

This document describes release artifacts, SBOMs, provenance, image signing, Trivy scanning, and VEX handling for Melodarr Proxy and Melodash.

## Release Artifacts

Each tagged release publishes two container images:

```text
ghcr.io/melodarr/melodarr-proxy:<version>
ghcr.io/melodarr/melodarr-proxy-melodash:<version>
```

The release workflow also publishes:

- `proxy-sbom.spdx.json`
- `melodash-sbom.spdx.json`
- OCI build provenance attestations generated by Docker Buildx
- OCI SBOM attestations generated by Docker Buildx
- keyless Cosign signatures for both images

The `latest` tags are only published after validation passes.

## SBOMs

SBOMs are generated with Anchore's SBOM action and attached to the GitHub release.

Expected release assets:

```text
proxy-sbom.spdx.json
melodash-sbom.spdx.json
```

Download them from the GitHub release page or with `gh`:

```bash
gh release download v0.3.42 \
  --pattern '*sbom.spdx.json' \
  --repo melodarr/melodarr-proxy
```

The container registry also receives Buildx-generated SBOM attestations for each pushed image.

## Provenance And Attestations

The release workflow builds images with:

```yaml
provenance: mode=max
sbom: true
```

This publishes OCI attestations alongside the images in GHCR. These attestations describe build inputs and build metadata for the pushed image manifests.

Inspect image provenance with Docker Buildx:

```bash
docker buildx imagetools inspect ghcr.io/melodarr/melodarr-proxy:0.3.42
docker buildx imagetools inspect ghcr.io/melodarr/melodarr-proxy-melodash:0.3.42
```

## Cosign Image Signing

Images are signed with keyless Cosign using GitHub Actions OIDC.

Verify the proxy image:

```bash
cosign verify \
  --certificate-identity-regexp 'https://github.com/melodarr/melodarr-proxy/.github/workflows/release.yml@refs/tags/v.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/melodarr/melodarr-proxy:0.3.42
```

Verify the Melodash image:

```bash
cosign verify \
  --certificate-identity-regexp 'https://github.com/melodarr/melodarr-proxy/.github/workflows/release.yml@refs/tags/v.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/melodarr/melodarr-proxy-melodash:0.3.42
```

Use the exact version tag you plan to deploy. Avoid verifying `latest` for change-control decisions because it moves.

## Trivy Policy

The release workflow runs Trivy against both images:

```text
ghcr.io/melodarr/melodarr-proxy:<version>
ghcr.io/melodarr/melodarr-proxy-melodash:<version>
```

Current policy:

- scan OS and library vulnerabilities
- fail the release on `HIGH` or `CRITICAL`
- ignore unfixed vulnerabilities
- disable the generic Trivy VEX notice in CI output

Workflow settings:

```yaml
ignore-unfixed: true
vuln-type: os,library
severity: CRITICAL,HIGH
exit-code: 1
```

If Trivy blocks a release, the default action is to update dependencies or base images and rerun the release.

## VEX Policy

VEX is used only when a vulnerability is detected but is not exploitable in this project.

A VEX statement may be appropriate when:

- the vulnerable code is present only in build tooling and not shipped in the runtime image
- the vulnerable package is unreachable from the application
- the vulnerable feature is disabled or not used
- the finding is in an unused transitive dependency that cannot be invoked

A VEX statement is not appropriate when:

- a fixed version is available and can be adopted safely
- the vulnerable code is reachable from HTTP request handling
- the impact is unclear
- the package is part of runtime startup, provider calls, auth, settings, or request parsing

Before adding VEX, document:

- vulnerability id
- affected package and version
- affected image
- why the vulnerable path is not exploitable
- what test or code inspection supports that decision
- who reviewed the decision

VEX files, when added, should live under:

```text
security/vex/
```

The release workflow should only be adjusted to consume VEX files after the VEX statement is committed and reviewed. The directory currently contains a policy README and no active VEX exception.

## Operator Verification Checklist

Before deploying a release in a stricter environment:

```bash
cosign verify \
  --certificate-identity-regexp 'https://github.com/melodarr/melodarr-proxy/.github/workflows/release.yml@refs/tags/v.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/melodarr/melodarr-proxy:<version>

cosign verify \
  --certificate-identity-regexp 'https://github.com/melodarr/melodarr-proxy/.github/workflows/release.yml@refs/tags/v.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/melodarr/melodarr-proxy-melodash:<version>
```

Then download and archive the SBOMs from the GitHub release.

## Release Workflow Summary

The release workflow:

1. runs lint and tests
2. builds proxy and Melodash images
3. publishes version tags
4. publishes Buildx provenance and SBOM attestations
5. signs both images with Cosign
6. verifies GHCR image availability
7. generates release SBOM files
8. scans both images with Trivy
9. confirms public pull access for the proxy image
10. runs canary validation
11. publishes `latest`
12. signs `latest`
13. creates the GitHub release with SBOM attachments
